06 Calling the API directly

Three calls: get a token, verify a card, fetch the images. Examples use a local DEV instance; swap the host for your environment.

Before you start

You need a client id and client secret from whoever runs the service. In DEV these are postalid-demo-client and dev-only-secret-change-me.

  1. Exchange your credentials for a token

    Send the client id and secret using HTTP Basic authentication. Ask for the scopes you need, separated by a space.

    bashstep 1 — authenticate
    curl -u 'postalid-demo-client:dev-only-secret-change-me' \
  -d 'grant_type=client_credentials' \
  --data-urlencode 'scope=postalid.verify postalid.images' \
  http://localhost:8080/oauth2/token

    The reply:

    jsonresponse
    {
  "access_token": "eyJraWQiOiJiYjc3OWMwMS0yNWQzLTRhYWMt...",
  "scope": "postalid.images postalid.verify",
  "token_type": "Bearer",
  "expires_in": 300
}

    The token lasts 300 seconds. Re-use it across requests rather than fetching one per call, and request a new one when you get a 401.

  2. Verify a card

    Send the token as a bearer credential, with the five card fields as JSON.

    bashstep 2 — verify
    # Capture the token into a variable first
TOKEN=$(curl -s -u 'postalid-demo-client:dev-only-secret-change-me' \
  -d 'grant_type=client_credentials' \
  --data-urlencode 'scope=postalid.verify postalid.images' \
  http://localhost:8080/oauth2/token | jq -r .access_token)

curl -X POST http://localhost:8080/api/v1/verify \
  -H "Authorization: Bearer $TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{
        "postalRefNo": "A11230000001",
        "firstName":   "Juan",
        "middleName":  "Santos",
        "lastName":    "Dela Cruz",
        "dateOfBirth": "1990-01-31"
      }'

    A match:

    json200 — valid
    {
  "result": "VALID",
  "verifiedAt": "2026-08-30T08:35:04.526Z",
  "requestId": "7038dc89-3bf6-4b9e-b423-309586eef8d1",

  // What the card itself prints, and nothing beyond it.
  "cardholder": {
    "postalRefNo": "A11230000001",
    "firstName":   "JUAN",
    "middleName":  "SANTOS",
    "lastName":    "DELA CRUZ",
    "suffix":      null,
    "dateOfBirth": "1990-01-31",
    "gender":      "F",
    "nationality": "Filipino",
    "address": {
      "houseBldgLot": "BLK 7 LOT 2",
      "subdivision":  "GREENVIEW SUBDIVISION",
      "barangay":     "BARANGAY SAN ROQUE",
      "city":         "City of Calamba",
      "province":     "BTG",
      "postalCode":   "4027",
      "country":      "PHL"
    },
    "issuingPostOffice": null,
    "enrolledOn":        "2026-08-01"
  },

  // Derived from the production date, never supplied by the source.
  "validity": {
    "issuedOn":        "2026-08-03",
    "expiresOn":       "2029-08-03",
    "status":          "ACTIVE",
    "daysUntilExpiry": 1069,
    "derived":         true
  },

  "images": {
    "photo":     "/api/v1/images/Op4OPoAUFkBZjIVlmfXEHtRPpun-I3_5WoOdpU20_Z8",
    "signature": "/api/v1/images/0ca-q-A1xDzxkTWwoakbT8bwGQba4ZeXWlRnhkUhNQc"
  },
  "imagesExpireIn": 300
}

    No match:

    json200 — invalid
    {
  "result": "INVALID",
  "verifiedAt": "2026-08-19T09:23:20.133Z",
  "requestId": "4c1ff9f0-a2d7-4a64-a855-a0053077a90b"
}

    Clients granted the postalid.diagnostics scope receive a reason object naming every mismatched field:

    json200 — invalid, with diagnostics
    {
  "result": "INVALID",
  "verifiedAt": "2026-08-30T08:36:34.479Z",
  "requestId": "b6b8b4de-1362-4881-936d-70b21e0bc769",
  "reason": {
    "code": "FIELD_MISMATCH",
    "mismatchedFields": ["lastName", "firstName", "dateOfBirth"],
    "message": "3 field(s) did not match the stored record"
  }
}
    reason.codeMeaning
    FIELD_MISMATCHOne or more submitted fields did not match; see mismatchedFields
    NO_SUCH_RECORDNo record carries that reference number
    CARD_NOT_ISSUEDThe record exists but no card was produced
    RECORD_DELETEDThe record exists but has been deleted
    CARD_EXPIREDPast expiry, where the deployment treats that as invalid
    Why this needs its own scope

    mismatchedFields lists every field that failed, not just the first, so correcting one typo does not send you round the loop for a second you were never told about. Without the scope the reason key is absent and all failures stay identical.

    Field-level detail is exactly what makes a verification endpoint usable for harvesting: told which field was wrong, a caller can confirm a guess about a stranger one field at a time, and NO_SUCH_RECORD reveals whether any given reference number exists at all. Granting this scope is a decision to trust a specific client with that capability. Request it only if you genuinely need it.

    What the cardholder block will never contain

    The rule is only what is printed on the card. You are holding that card, so echoing its contents lets you spot a tampered one while disclosing nothing you could not already read.

    Present on the enrollment record and deliberately withheld: parents’ names, mobile number, email, TIN, CRN, GSIS, PhilHealth, HDMF, employer, occupation, work address, place of birth, physical description and payment records. Place of birth and the government identifiers are the sharpest omissions — both are widely used as knowledge-based authentication secrets, so disclosing them would actively enable impersonation.

    Expiry is derived — read validity.status

    The source data has no expiry column. expiresOn is the card production date plus a configured period, three years by default, which is why every response carries derived: true. Treat it as indicative.

    An expired card still returns VALID, with validity.status set to EXPIRED. The identity checked out, which is a different fact from the card being current — collapsing the two would stop you telling a lapsed card from a forged one.

    Both are HTTP 200 — branch on result, not status

    A card that does not check out is not an error. The request was understood, authorized and answered; the answer happens to be no. Reserving 4xx for genuine protocol faults means your client can treat 4xx and 5xx uniformly as "fix the call or retry", without special-casing a legitimate negative result. The presence of the images key is the only structural difference between the two bodies.

  3. Fetch the images

    Only on a VALID result, and only with the postalid.images scope. The paths come straight from the verify response.

    bashstep 3 — images
    curl "http://localhost:8080/api/v1/images/viUgLKKfOBKS_269kcgJkrwZWoCjcNTuQYuy89zQYfI" \
  -H "Authorization: Bearer $TOKEN" \
  -o photo.jpg
    Read the Content-Type header

    The photograph comes back as image/jpeg and the signature as image/png. Signatures are captured as TIFF, which no browser renders, so they are converted on the way out; the photograph is already web-safe and is passed through untouched. Do not assume a format from the URL.

    Image references expire after 300 seconds and allow five fetches. Fetch promptly; never store one as though it were a stable URL.

The same three calls in PowerShell

On Windows PowerShell, curl is an alias for Invoke-WebRequest and behaves differently. Use these instead:

powershellfull sequence
# 1. Token
$pair  = [Convert]::ToBase64String([Text.Encoding]::ASCII.GetBytes(
           'postalid-demo-client:dev-only-secret-change-me'))
$token = (Invoke-RestMethod -Method Post -Uri 'http://localhost:8080/oauth2/token' `
           -Headers @{ Authorization = "Basic $pair" } `
           -Body @{ grant_type = 'client_credentials'
                    scope      = 'postalid.verify postalid.images' }).access_token

# 2. Verify
$body = @{
  postalRefNo = 'A11230000001'
  firstName   = 'Juan'
  middleName  = 'Santos'
  lastName    = 'Dela Cruz'
  dateOfBirth = '1990-01-31'
} | ConvertTo-Json

$result = Invoke-RestMethod -Method Post -Uri 'http://localhost:8080/api/v1/verify' `
            -Headers @{ Authorization = "Bearer $token" } `
            -ContentType 'application/json' -Body $body
$result.result

# 3. Images, if valid
if ($result.result -eq 'VALID') {
  Invoke-WebRequest -Uri ('http://localhost:8080' + $result.images.photo) `
    -Headers @{ Authorization = "Bearer $token" } -OutFile photo.jpg
}

Client implementation rules

Branch on result
Never on the HTTP status. A non-matching card is 200.
Cache the token briefly
Re-use for its five-minute life; refresh on 401 rather than assuming a fixed lifetime.
Never retry an INVALID
It is a final answer. Repeating it burns rate limit and shows up in the audit trail as enumeration.
Retry 429 after Retry-After
And 5xx with backoff. Never retry a 400 or 403 unchanged — the call itself is wrong.
Do not cache image bytes
They are served no-store. Treat them with the same care as the card itself.
Keep the requestId
Quote it in support requests; it ties your call to the audit trail.

Using Swagger UI to make a real call

  1. Open /swagger-ui.html
  2. Click Authorize

    Enter your client id and secret, and tick the scopes you need.

  3. Expand POST /api/v1/verify and choose Try it out
  4. Edit the example body and click Execute

    The page shows the equivalent curl command, the response body and the response headers.

Input is checked against an allow-list and rejected if it does not fit. Nothing is silently stripped — a name containing <, digits or control characters produces a 400, not a sanitized lookup.

Errors

Errors are RFC 9457 problem documents with content type application/problem+json.

{
  "type":   "https://postalid.example/problems/validation-failed",
  "title":  "Validation Failed",
  "status": 400,
  "detail": "One or more fields are missing or malformed.",
  "errors": {
    "postalRefNo": "Postal reference number must be 8 to 20 letters or digits",
    "firstName":   "First name is required"
  }
}

Validation errors name your fields, because those are your own inputs and naming them is how you fix the call. Everything else is generic — a 500 returns a reference and nothing more, with the detail confined to the server log.

Rate limits

BudgetDefault
Verifications per client per minute300
Verifications per source address per minute100
Image fetches per client per minute600

Both verification budgets must pass. Tokens refill continuously rather than resetting on the minute, so a caller that paces itself is never blocked by a boundary.

Every successful verification publishes the caller’s remaining budget:

response headersbudget
RateLimit-Limit: 300
RateLimit-Remaining: 299
RateLimit-Policy: 300;w=60
Repeated failures are throttled separately

A caller returning INVALID twenty times in a row is held off for five minutes, independently of the per-minute budget. A legitimate integration checks cards people actually hold, so its failure rate is low; a long unbroken run of failures is what walking a range of reference numbers looks like. One success clears the run, so an occasional typo never accumulates.
